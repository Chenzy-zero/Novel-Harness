# workflow.md — Long Novel Workflow v0.1（强约束）

## 0. 职责与事实分层
**作者是主线与核心设定的最终批准人**。`bible/`、`outline/` 的 APPROVED 文档为规划正史；正文正式合并后成为事件证据。`state/` 是可重建的当前状态物化视图；`handoffs/` 是可用但可能有损的跨会话摘要；GitHub Issues 是 workflow 状态镜像与审批入口。发生冲突时查证正文和批准记录，不以 Issue 的新旧覆盖正史。

四种标识：`DRAFT`（草案）、`PROPOSED`（待确认）、`APPROVED`（作者确认）、`BLOCKED`（有雾）。未经明确授权，不从草案升级到 APPROVED。

## 1. 初始化与 Grilling（Gate A）
- 阅读作者已有要求；列出缺口，不重复已答问题。
- 核对题材、读者/平台、视角、叙事基调、作品卖点、开篇钩子、世界规则、主角欲望与代价、核心矛盾、终局方向、篇幅、可接受尺度、禁区、是否同人/原创。
- 提供 2–3 种有鲜明利弊的备选，不虚构作者选择。
- 将作者明确批准的内容归档于 `project/brief.md`、`bible/`，决策证据归档于 `project/decisions.md`；未确认问题进入 `project/questions.md`。
- 重大新人物、设定更改和核心反转必须进入同一 approval 流程；不以“聊过”自动视为批准。

## 2. 大纲与开写门禁（Gate B）
只有满足下列条件，才可开始第 1 章正式写作：
1. 已批准的基本世界/限制/能力体系、主角动机、核心冲突、作品基调和近期剧情走向。
2. 分卷/大剧情弧主线已成形，至少可覆盖前100章；故事不是为了填满数量编段子。
3. ``outline/first-100.md` 有 **1–100 每章独立的 1–3 句事件 / 冲突 / 推进与钩子**；每 10 章有小目标，每 30 章有收束/升级/悬念。
4. 前30章需有更细的章节契约：人物、地点、目标、冲突、事件因果、情绪变化、显隐伏笔、结尾钩子、需更新状态。
5. 首100章相关主要人物、重要势力/规则、预设关键伏笔均已建档，未知内容用待决项表示；**核心 BLOCKED 项清零**。
6. `project/brief.md` 的 `planning_status` 改为 `APPROVED` 并有作者批准记录；验证脚本的 Gate B 模式通过。
7. 建议先单独产出**第1–3章试写**供作者确认文风；若用户坚持每次只写30章，可将试写限定为不入 canon 的样稿，正式发布仍按30章批次。

## 3. 恢复上下文（每次执行、与状态检索）
`current` → 最近 handoff → 前一 handoff（仅用于稽核）→ 本批次计划 → 涉及人物、剧情弧与伏笔的**精确文档** → 最后相关章节原文 → GitHub Issue 状态。不要一口气读取全书；读取范围以影响面扩大。若摘要与正文冲突，以正文及作者批准资料判定，更新状态并记录纠错。

## 4. 一个正式批次 = 30章（Gate C）
**开始**：仅允许连续编号 `0001–0030`、`0031–0060`……；禁止半批次对外宣称完成。总目标约每章2000中文字，默认建议 **1800–2200 汉字**（统计汉字 Unicode U+3400–U+9FFF，正文不含章节标题/元信息），可在 `project/brief.md` 由作者覆盖。

每章内部事务：
1. 载入 chapter contract、所有相关角色/物品/地点/线索的状态及该场景已知信息。
2. 写草稿；检查因果、口吻、人物欲望、冲突、规则、时间、伏笔、钩子，避免机械流水账与 AI 套话。
3. 提取**证据化状态变更**：谁在何时何处、知道什么、关系与情绪如何变化、物品转移、哪些伏笔新埋/推进/兑现、剧情点完成与否。
4. 为新重要角色建 `CHAR` 卡及 Issue；更新关联 `ARC` / `BEAT` / `THREAD` 与状态台账，记录 `source_chapter` 与证据句/段落。
5. Issue 可在草稿期先标注 `draft/pending`，但**不得把尚未发布的内容当作已发布正史**。GitHub Issue 与本地状态必须在本批次完成时全量对账。
6. 做每章校验，发现“有雾”立即升级 `BLOCKED` 并 grilling；不用未经同意的设定来填洞。
7. 只在下一章契约与本章结局逻辑连续时继续。

**批次结束**：校验30篇齐备、编号无缺重、每章长度、人物/规则/时序/伏笔、未来线索去向；汇编 `handoffs/0001-0030.md`，其中必须**融合上一 handoff 累计基线 + 当前30章的原文事实**（不是简单复制两份摘要）。更新 `state/current.md`。检查 GitHub issue 双向链接和未同步队列。

**提交条件**：30章全部通过 Gate C；Issue 无 `sync_pending`；handoff 的起止章数、主线、角色、伏笔、下一30章路线完整；提交一个可审阅 commit 到批次分支，`git push` 并创建 PR/合并（根据项目策略）。失败不得声称提交成功，也不得另起第31章。
为跨上下文长任务，可本地保存中间草稿/commit，但**不能提前把未完30章推为正式发布**。必要时经作者同意使用远端私有 draft 分支作为恢复点，并明确它不是已完结批次。

## 5. 每累计300章复盘（Gate D）
在 Gate C 完成后（第300、600、900……章），追加 `reviews/0001-0300.md` 等全量审计：
- 全部主线/分卷目标和偏航检测：承诺、兑现、冲突推进比例。
- 重要 NPC 是否无档、消失无交代、死亡后无解释复活；性格与关系是否突变。
- 伏笔从`open/progressing/paid/deferred`到目标兑现窗；滞留与遗漏列表。
- 全时间线、地理、能力限制、物品归属、知情人、身份秘密互相核对。
- `canon` 与 Issue 镜像差异、未决/矛盾证据、下一300章重排建议。
- 重大重排先向作者 grilling，经批准后修改 `outline`；复盘结论不应自动改写已发布章节。

## 6. GitHub Issues 状态管理
详见 `docs/issue-model.md`。只管理可持续追踪的单位：ARC、BEAT、CHAR、THREAD、AUDIT（可选 RULE）；普通对白、小动作、不重要的一次性路人**不上 Issue**。
每个 Issue 必须有稳定ID、对应仓库文档相对路径、state、last_changed_chapter、相关关联、更新依据。文档中反向写 issue URL。Issue 关闭 != 角色死亡。
状态发生变化时立即写入工作台账与 Issue（或待同步变更队列）；发布门禁要求无未处理变更。若更新 Issue 失败，保留 `sync_pending` 并 BLOCK，不允许“下批再说”。

## 7. 异常处理
- **单章质量不达标**：仅重写受影响章节，并重新计算后续影响，禁止不回滚状态就重新生成。
- **历史/设定矛盾**：列出原文证据、最新变更与修正选择；必要时回滚本批草稿。
- **重要决策不明**：记到 `project/questions.md`，说明阻塞哪些章节后向作者 grilling。
- **权限/网络/GitHub Issue 失败**：保留本地状态变更日志并设置 `sync_pending`，暂停正式发布；不得假装 issue 已更新。
- **只有部分批次**：继续补足30章或由作者取消，禁止把其命名为完整 handoff。
- **读不到 GitHub Issues**：可以讨论设定/准备大纲，不可通过 Gate C 正式发布。

## 8. GitHub 自动化工具（V0.2）
GitHub bootstrap、Issue manifest 和幂等同步统一参见 `docs/github-automation.md`。`novel-init` 调用 bootstrap，`novel-outline` / `novel-continue` 维护 `state/github-issues.json` 并执行 reconcile / sync。工具不等于完整 GitHub 状态镜像：Issue 证据、反向链接、状态变迁与 PR 门禁仍需核验。禁止把同步脚本成功等同于 Gate C 成功。
